# 见山Terrascope · 项目结构讲解（新手版）

> 本文档用给新人讲解的方式，梳理项目的整体结构：每个文件夹干什么、数据从哪来到哪去、p0-server 核心文件分别负责什么。

---

## 项目一句话定位

**见山Terrascope** 是一个“乡村文旅数字底座”——把丽江玉龙雪山/拉市海区域的气象、空气质量、民宿、IoT 设备等多源数据统一抓过来、存起来、算一算（比如“今天能不能看到雪山”），再通过 API 和网页对外提供。参加的是 2026 天津新工科大赛。

---

## 顶层目录：每个文件夹干什么的

```
见山Terrascope_新工科大赛/
│── 01_参赛项目报告/        ← 写给评委看的项目报告（Markdown 终版）
│── 02_测试验证/            ← pytest 跑过 10/10 的截图记录 + demo 接入实拍
│── 03_民宿数据/            ← 民宿采集规范、CSV 模板、合作商家简介
│── 04_合规与申报/          ← 附件1 填报表、合规自查清单、交材料对照清单
│── 05_汇报材料/            ← 答辩 PPT / PDF、8分钟讲稿、离线演示 HTML
│── yunqi-naxi/             ← ★ 项目源码（代码全在这里）
└── README.md               ← 顶层说明（材料状态、时间线、目录地图）
```

**简单理解**：`01-04` 和 `05` 是“文职”——报告、合规、答辩材料；`yunqi-naxi/` 才是真正的代码。

## `yunqi-naxi/`：源码总览

```
yunqi-naxi/
│── p0-server/     ← ★ 后端核心（Python / FastAPI）
│── web/           ← 前端演示页（一个 HTML + ECharts）
│── scripts/       ← 辅助脚本（生成路演话术等）
│── assets/        ← 三张图：落地版图、技术架构图、社会价值图
└── docs/          ← 部署指南 + 修订对照说明
```

- **`web/`**：只有一个 `见山Terrascope_demo.html`，是答辩时双击就能打开的离线演示页，用 ECharts 画图表，调后端 API 拿数据。`vendor/` 里放了 echarts、tailwind、html2canvas 的离线副本。
- **`assets/`**：三张 SVG/PNG 图，给 PPT 和报告用的。
- **`scripts/`**：`gen_路演话术.py`——生成路演文案的辅助脚本，跟数据管道无关。

│                      数据来源（四源）                         │

│  天源① Open-Meteo    免费无密钥，历史+预报气象                 │

│  物源④ ESP32 设备    自建 IoT 上报（预留协议，P0 即可联调）    │
│  人源⑤ 民宿采集表    CSV 人工采集，脚本校验入库               │
└───────────────├──────────────────────────────────────────────────────┐
           │  services/ 适配层                  │  scripts/load_stays.py

│                                                             │
│  sources 表        9类数据源注册表（溯源元数据）               │
│  observations 表   天/地源观测数据（每条带 source_key 溯源）  │
│  devices 表        ESP32 设备注册（key 存 sha256）           │
│  device_observations 表  设备上报数据                        │
│  stays 表          民宿名录（脱敏，public=1 才对外）          │
│  ingest_logs 表    采集日志（成功/失败/行数，管道状态可见）    │
└────────────────────────────────────────────────────────────────────────────────────┐
                           │
          ┌───────────────├──────────────────────┐
          │                │                │
          ▼                ▼                ▼
   FastAPI 路由       P1 观山模型        ECharts 演示页
   (routers/api.py)   (p1/mountain_      (web/demo.html)

**一句话版**：外部免费 API → `services/` 适配抓取 → `ingest.py` 降频+去重+入库 → SQLite → FastAPI 对外提供接口 → 前端 ECharts 调接口画图。

## `p0-server/` 核心文件逐一讲解

### 目录结构

```
p0-server/
│── app/                     ← 主代码包
│   │── main.py              ← 入口：创建 FastAPI，挂路由，启动时建表+注册数据源
│   │── config.py            ← 全局配置：数据库 URL、丽江坐标、降频间隔、API Key
│   │── db.py                ← 数据库连接：SQLAlchemy engine + session，SQLite/PG 双兼容
│   │── models.py            ← ORM 模型：6 张表的字段定义
│   │── schemas.py           ← Pydantic 模型：API 请求/响应的数据校验格式
│   │── ingest.py            ← ★ 采集调度器：降频判断→调 services 抓数据→去重入库→写日志
│   │── routers/
│   │   └── api.py           ← ★ 全部 API 路由：仪表盘/数据源/民宿/设备/管理 5 组
│   │── services/            ← 数据源适配层（每个文件对接一个外部 API）
│   │   │── open_meteo.py    ← Open-Meteo：历史归档+预报抓取，含规则版观山指数公式
│   │   │── qweather.py      ← 和风天气：实时天气（无 Key 自动跳过）
│   │   └── cnemc.py         ← 生态环境部：P0 抛 NotImplementedError，预留接口契约
│   └── p1/
│       └── mountain_model.py← ★ P1 观山指数 ML 模型：逻辑回归训练/预测/元数据保存
│── data/
│   │── yunqi.db             ← SQLite 数据库文件（运行后自动生成）
│   └── model/
│       │── mountain_index_lr.joblib     ← 训练好的 LR 模型文件
│       └── mountain_index_meta.json     ← 模型元数据（准确率/混淆矩阵/窗口等）
│── scripts/
│   └── load_stays.py        ← 民宿 CSV 入库脚本：校验+脱敏红线+幂等写入
│── tests/
│   │── test_api.py          ← API 冒烟测试（含真实 Open-Meteo 调用）
│   │── test_load_stays.py   ← 民宿入库行为测试（脱敏/幂等/更新）
│   └── fixtures/
│       └── stays_fixture.csv← 测试用的民宿 CSV 样本
│── requirements.txt         ← Python 依赖（fastapi/sqlalchemy/sklearn 等）
└── README.md                ← 后端架构说明+快速开始+接口文档
```

### 逐文件说明

| 文件 | 职责 | 新人理解 |
|------|------|----------|
| **`main.py`** | FastAPI 应用入口 | `uvicorn app.main:app` 就是从这里启动。启动时自动建表、注册 9 类数据源，然后把 5 组路由挂上去。 |
| **`config.py`** | 全局常量 | 丽江两个坐标（玉龙雪山 27.12°N、拉市海 26.71°N）、降频间隔（Open-Meteo 60min / 和风 30min）、数据库 URL、API Key。改配置只改这里。 |
| **`db.py`** | 数据库引擎 | 用 SQLAlchemy 连 SQLite（开发）或 PostgreSQL（生产）。`get_db()` 是 FastAPI 依赖注入用的“给路由一个 db session”函数。 |
| **`models.py`** | 6 张表的 ORM 定义 | `Source`=数据源注册表、`Observation`=天/地源观测、`IngestLog`=采集日志、`Device`=IoT 设备、`DeviceObservation`=设备上报、`Stay`=民宿。每条 Observation 都带 `source_key` + `fetched_at`，实现**逐条溯源**。 |
| **`schemas.py`** | API 入参/出参格式 | Pydantic 模型，用于自动校验请求体和生成 Swagger 文档。比如 `DeviceObsIn` 定义了 ESP32 上报一条数据的 JSON 结构。 |
| **`ingest.py`** | **采集调度核心** | 三件事：①`_allowed()`降频控制——距离上次抓取太近就跳过；②`_save()`幂等入库——(源+站点+指标+时间)唯一约束，重复不写；③`run_all()`依次调三个源的采集函数。 |
| **`routers/api.py`** | **全部 API 路由** | 5 组：`/api/dashboard`（观山指数+最新观测）、`/api/sources`（数据源溯源）、`/api/stays`（脱敏民宿名录）、`/api/devices`（ESP32 注册/上报/OTA）、`/api/admin`（手动触发采集/训练模型/查日志）。 |
| **`services/open_meteo.py`** | Open-Meteo 适配 | `fetch_archive()`=历史归档、`fetch_forecast()`=未来预报、`fetch_past_hourly()`=预报接口 past_days 模式（P1 训练标签源，能见度真实可得）、`mountain_index_rule()`=规则版观山指数公式。 |
| **`services/qweather.py`** | 和风天气适配 | 只调了一个“实时天气”接口，返回标准化观测列表。无 Key 时返回 `(None, '跳过')`，不阻塞其他管道。 |
| **`services/cnemc.py`** | 生态环境部适配 | P0 阶段该平台没有官方 JSON API，所以只 `raise NotImplementedError`，预留了返回结构，P1 接真实实现时上层代码零改动。 |
| **`p1/mountain_model.py`** | **观山指数 ML 模型** | 用 Open-Meteo 近 92 天历史能见度做标签（白天中位数≥15km=可观山），4 个特征（云量/降水/湿度/风速），逻辑回归+walk-forward 时序交叉验证。`train()` 训练并保存 joblib+json，`predict()` 加载模型出概率×100 作为指数。 |
| **`scripts/load_stays.py`** | 民宿入库脚本 | 读 CSV → 校验（必填/枚举/stay_id 格式）→ 脱敏红线扫描（手机号/7位以上数字→整行拒绝）→ 幂等写入（内容哈希未变则跳过）。 |
| **`tests/test_api.py`** | API 冒烟测试 | 覆盖：健康检查、数据源注册表、真实 Open-Meteo 抓取+溯源字段、观山指数契约（0-100）、ESP32 全流程（注册→上报→查→OTA）、民宿脱敏（public=1 才出、敏感字段永不外泄）。 |
| **`tests/test_load_stays.py`** | 民宿入库测试 | 覆盖：脱敏红线拒绝、幂等重跑不重复、数据变更走 UPDATE、dry-run 不产生数据库。 |

## 关键设计理念（新人值得知道的）

- **降频防超限**：免费 API 有调用额度，`config.MIN_INTERVAL_MIN` 控制最小间隔，窗口内自动跳过。
- **幂等去重**：观测表有 `(source_key, site, metric, ts)` 唯一约束，重复抓取不产生脏数据。
- **全程溯源**：每条观测带 `source_key`（来自哪个源）和 `fetched_at`（什么时候抓的），`GET /api/sources` 返回全部 9 类数据源元数据。
- **P0 规则版 → P1 模型版**：观山指数有两条路径——没模型文件时用规则公式，训练后自动切换为逻辑回归模型，接口契约不变。
- **ESP32 预留协议**：注册→`X-Device-Key` 认证上报→OTA 版本协商，硬件到位即插即用，云端零修改。
- **脱敏红线**：民宿数据永不对外暴露联系方式/授权编号/内部备注；`public=0` 的记录只做内部统计。
